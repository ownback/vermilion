# U1: the UCLK hard minimum through the DAL mailbox (2026-11-26)

Item U1 of the B1 design ([2026-11-26-kernel-bringup-design.md](2026-11-26-kernel-bringup-design.md), section 3 and
section 7, finding A). Branch `ownback/uclk-dal`, VermilionBoot b167 (the B1 plan reserves b164-b166 for K1-K3). Code
read on `fork/main`. Linux read in a scratch folder outside git: tag v6.8 and master at `ebb7a8dc1e74` (2026-11-25);
line numbers below are `v6.8 :n / master :m`. Linux's behaviour on the XTX machine is from the 78 mode-set traces of
2026-11-20 and 2026-11-21 (kernel 7.2.15, `amdgpu_dc_wreg` tracepoint, `tools/capture/linux_display_capture.py`; the
traces stay outside git). macOS state read-only on the XTX machine (boot of 2026-11-26 00:51, VermilionBoot b162).
Nothing here was booted: everything about the new code on hardware is (unverified).

## Summary

- **Today, two senders of the driver-mailbox `SetHardMinByFreq` (0x1B) on every boot of the XTX machine.** The daemon
  (`uclk.sh pin 456`, after the bring-up and after `done`; `/var/log/phxboot.log`: `msg 0x1b arg 0x000201c8 ... (OK)`)
  and the kext's macOS mode path (`phxp0::macSet`, the 60 -> 144 Hz step before the 240 Hz entry:
  `debug.phxpipe0_stat` reads `mac=1 uclk_pins=1`, `debug.phxpipe0_uclk` reads 456). `idle_dpm.sh` releases and
  re-pins through the same message (`uclk.sh unpin` / `pin 456`).
- **Linux never sends 0x1B on SMU 13.0.0** (section 2.3). Its display code (DC) sets the UCLK hard minimum through the
  DAL mailbox: DALSMC `SetHardMinByFreq` (9), argument `(PPCLK_UCLK 2 << 16) | MHz`, on registers 0x1628A / 0x16273 /
  0x16274, then `ReturnHardMinStatus` (0x15) until the PMFW reports it done.
- **Linux's values on this card:** level 0 (96 MHz) after every mode set, at every mode (all 72 traces that carry a UCLK
  message end at 96). The top level (1249 MHz) only inside a mode set into or out of a 240 Hz mode, where DC turns
  firmware-assisted memory clock switching (FAMS) on or off. Linux never sends 456.
- **The change:** `uclk.sh pin` = DAL hard minimum at the top level (Linux's value while the display can't take a UCLK
  switch), `uclk.sh unpin` = DAL hard minimum at level 0 (Linux's value after a mode set); the levels come from the PMFW
  through the same mailbox. Kext b167: `macSet` sends no UCLK message (`debug.phxpipe0_uclk` takes only 0) and none
  through the driver mailbox at all; the debug selector refuses driver-mailbox 0x1B and 0x1C. The daemon keeps its two
  pin points and `idle_dpm.sh` its release and watchdog.
- **Open (section 7):** at 240 Hz Linux's low UCLK floor goes with FAMS, which macOS doesn't do. `idle_dpm.sh` has
  released UCLK at 240 Hz since 2026-11-23 (43 releases in the log, no underflow re-pin); U1 keeps that and only
  changes the mailbox. The hw-safety review counts that release as a departure from Linux carried over from before
  U1: its own item (TODO 01). The pin at the top level costs more idle power than 456 did, for as long as the pin holds
  (not measured).

## 2. What Linux does

### 2.1 The mailbox and the message

- DAL mailbox registers: `dcn32_clk_mgr_smu_msg.c` v6.8 :33-35 / master :33-35: `mmDAL_MSG_REG 0x1628A`,
  `mmDAL_ARG_REG 0x16273`, `mmDAL_RESP_REG 0x16274` (the kext's `dalMessage`, `phx_psp_smu.cpp`, uses the same three).
- One transaction, `dcn32_smu_send_msg_with_param` v6.8 :68 / master :72: wait up to 2 s for RESP != 0, RESP = 0,
  ARG, MSG, wait for RESP, read ARG back when RESP = 1 (OK).
- Message IDs, `dc/clk_mgr/dcn32/dalsmc.h` (the same in both): `SetHardMinByFreq 0x9` (:47), `SetHardMaxByFreq 0xA`,
  `GetDpmFreqByIndex 0xB` (:49), `SetFclkSwitchAllow 0x11` (:55), `SetAlwaysWaitDmcubResp 0x14` (:58),
  `ReturnHardMinStatus 0x15` (:59); `CHECK_HARD_MIN_CLK_DPREFCLK 0x4`, `_UCLK 0x20` (:62-67).
- `dcn32_smu_set_hard_min_by_freq` v6.8 :271 / master :281: argument `(clk << 16) | freq_mhz`; then, when
  `dcn32_get_hard_min_status_supported` (v6.8 :184-187 / master :194-197: GC 11.0.0 with PMFW >= 0x4E6A00; the XTX
  machine's PMFW is 0x4E8700, 78.135.0, [linux-reference](2026-11-23-linux-reference.md)),
  `dcn32_smu_wait_get_hard_min_status` (v6.8 :216 / master :226): `ReturnHardMinStatus` (argument 0) until the answer
  has DPREFCLK | UCLK (0x24), 1 ms apart, 2 s at most (v6.8 :226, :252, :257 / master :236, :262, :267); a read not
  answered OK counts as the whole 2 s and ends it (v6.8 :147). A status that never comes is only logged.
- The UCLK levels: `dcn32_init_single_clock` (v6.8 :132 / master :132) reads them through the same mailbox with
  `dcn30_smu_get_dpm_freq_by_index` (`dcn30_clk_mgr_smu_msg.c` v6.8 :259-273 / master :261; argument `(clk << 16) |
  level`): index 0xFF = the count (bit 31 = fine-grained: 2 levels), then each index. `dcn32_get_memclk_states_from_smu`
  (v6.8 :969 / master :1043) sets `max_memclk_mhz` = the last level (v6.8 :998-999 / master :1069-1070). DC sends
  nothing at all when `GetSmuVersion` (DAL 2) fails (`dcn32_init_clocks` v6.8 :179 / master :181: `smu_present`).

### 2.2 When

- **At display init**, after the SMU block's init (IP block order: `amdgpu_discovery.c` v6.8 :2673 smu, :2678 display /
  master :4066, :4071): `dcn32_init_clocks` reads the tables; `dcn32_init_hw` (`hwss/dcn32/dcn32_hwseq.c` v6.8 :747 /
  master :813) sends the DAL watermark table (`notify_wm_ranges`, v6.8 :937-938 / master :1003-1004) and
  `SetHardMaxByFreq` UCLK = the top level unless the DC-mode soft max is on (v6.8 :940-941 / master :1006-1008). The
  soft max is never on with amdgpu: `dc_enable_dcmode_clk_limit` (dc.c v6.8 :4967 / master :6647) has no caller in
  `amdgpu_dm` (v6.8, master).
- **Every update, `dcn32_update_clocks`** (`dcn32_clk_mgr.c` v6.8 :589 / master :633), called with `safe_to_lower`
  false before a mode set (prepare: only raises) and true after it (optimize: may lower), `should_update_pstate_support`
  / `should_set_clock` (`clk_mgr_internal.h` v6.8 :374-389 / master :570-585):
  - p-state switching becomes unsupported (prepare) -> "to disable P-State switching, set UCLK min = max":
    `SetHardMinByFreq` UCLK `max_memclk_mhz` (v6.8 :674-690, the value at :688 / master :720-742, :739);
  - `SetAlwaysWaitDmcubResp` = `fw_based_mclk_switching` at every call (v6.8 :693-696 / master :744-747);
  - FCLK switch: `SetFclkSwitchAllow 1` when support turns on (optimize), 0 when it turns off (v6.8 :633-641, :703-707
    / master :677-686, :754-758);
  - p-state supported and the requested memory clock changed, or switching re-enabled -> `SetHardMinByFreq` UCLK =
    `dramclk_khz` (v6.8 :710-720 / master :761-777). `dramclk_khz` is DML's DRAM speed for the chosen voltage level
    (`dcn32_fpu.c` v6.8 :1657 / master :1637); 0 when no plane is fetching (v6.8 :1767-1770 / master :1742-1745).
- **Any switch into or out of a FAMS configuration**: `dcn32_prepare_bandwidth` (v6.8 :1752-1778 / master :1851-1880)
  "should disable MCLK switching first": p-state support forced off for the prepare call (so UCLK = the top level),
  back on at the optimize call.
- **FAMS** ("FPO", firmware-based vblank stretch): tried only when the natural switch is not possible, or possible only
  at a higher voltage level (`dcn32_fpu.c` v6.8 :2325-2332 / master :2337-2345), and kept only when it lowers the
  voltage level; `p_state_change_support |= fw_based_mclk_switching` (v6.8 :1667 / master :1647). It needs a DMCUB that
  reports FW-assisted MCLK switching, a refresh of 120 Hz or more, one stream (two with one in VACTIVE), a plane and
  FreeSync allowed on the stream (`dcn32_can_support_mclk_switch_using_fw_based_vblank_stretch`,
  `dcn32/dcn32_resource_helpers.c` v6.8 :527-598; `dc->caps.dmub_caps.mclk_sw` from the DMCUB caps, `dcn32_hwseq.c`
  v6.8 :959). macOS runs the GOP's DMCUB and sends no FAMS command, so on macOS DC would not use FAMS.

### 2.5 Our mode: 2560x1440, up to 240 Hz, VRR 60-240, one DP sink

- **Linux (with FAMS):** UCLK hard minimum 96 MHz and `SetAlwaysWaitDmcubResp 1` at 240 Hz; 96 and
  `SetAlwaysWaitDmcubResp 0` at 60 / 120 / 144; 1249 only inside a switch to or from 240.
- **Linux without FAMS, the macOS situation:** FAMS was chosen at 240 Hz, so by `dcn32_fpu.c` v6.8 :2325-2326 the
  natural switch was not possible at the lowest voltage level. Without FAMS DC keeps DML's answer: p-state unsupported
  (UCLK hard minimum = the top level) or supported only at a higher level (that level's UCLK, which the traces don't
  show). Which one needs DML's numbers (unverified). At 60 / 120 / 144 Hz FAMS plays no part: 96 is Linux's value there
  with or without it.

## 3. The replacement

Our boot has two UCLK states, mapped onto Linux's:

| Our state | Linux's equivalent | Message (DAL mailbox only) | Sent by |
|---|---|---|---|
| **pinned**: from the bring-up to the settled desktop (the GOP's watermarks, our mode switches, which skip Linux's UCLK raise and lower), and for the rest of a boot after an underflow | p-state switching unsupported: "UCLK min = max" (v6.8 :688) | `SetHardMinByFreq (2 << 16) | top level` (1249 on this card) | `uclk.sh pin`: `uclk_boot` (after the bring-up, which ends with `EnableAllSmuFeatures`, `bringup_navi31.sh:168`: Linux's order, SMU before display; and after `done`), `idle_dpm.sh`'s watchdog |
| **released**: the DAL watermark table sent, the desktop settled, 30 s without an underflow | after the mode set: UCLK = `dramclk_khz` (v6.8 :720) | `SetHardMinByFreq (2 << 16) | level 0` (96 on this card) | `uclk.sh unpin`: `idle_dpm.sh` step 3 |

Each `pin` / `unpin` sends, in Linux's order: `GetSmuVersion`, the UCLK table (`GetDpmFreqByIndex` 0xFF, then each
level), `SetHardMinByFreq`, then `ReturnHardMinStatus` until 0x24 (~2 s at most) on a PMFW >= 0x4E6A00; a status
read not answered OK ends the wait, as in Linux, with the hard minimum still acknowledged. Any other message not
answered = nothing further, exit 1, no `(OK)` (so `idle_dpm.sh` treats a failed release as a refusal and pins again). A
busy answer from the kext = again in 10 ms, ~2 s at most: Linux waits 2 s for the mailbox and then writes anyway
(v6.8 :71), the kext writes nothing while busy (`phx_psp_smu.cpp` `dalMessage`). A DAL timeout in a pin latches the
kext's `gDalDead` for the boot (every later SMU and DAL message refused without a register access); the old
driver-mailbox pin didn't latch it. The DAL debug allow-list already passes all four (`phx_debug.cpp`: 0x02, 0x0B and
0x09 with PPCLK_UCLK, 0x15; unchanged since b75): no new kext path for the daemon.

**Order against Linux's init:** the first DAL message is now `GetSmuVersion` after `EnableAllSmuFeatures`, Linux's
order (SMU block before display). Linux sends the DAL watermark table and `SetHardMaxByFreq` UCLK (`dcn32_init_hw`,
`dcn32_hwseq.c` v6.8 :937-941) before any hard minimum; here the watermark table goes out only at `idle_dpm.sh` step 3,
after the pin. That was already so for the 456 pin and for the kext's DISPCLK / DPPCLK hard minimums: not new with U1.

**Kernel (b167):** `macSet`'s UCLK step goes through `Env.dal` (after `pmfwIdle`), and `debug.phxpipe0_uclk` takes only
0 (none; any other value is EINVAL): Linux sends no UCLK raise for the 60 / 120 / 144 Hz switches on this card (section
2.4), the daemon's pin holds UCLK at the top level until the desktop anyway, and any other MHz would replace the
daemon's hard minimum (the last one sent wins) and could lower it, where Linux sends only a DPM level. The step stays in
`macSet` (tested through the header) for K11 (B1 condition 15). `Env.smu` and `p0Smu` are gone, so no kernel path sends
a driver-mailbox clock limit. The debug selector's driver-mailbox list refuses 0x1B and 0x1C; 0x19 / 0x1A / 0x1D-0x1F
stay. Old scripts on b167: every `pin` / `unpin` refused (`kr 0xe00002e2` in the log, no `(OK)`), so UCLK stays unpinned
for the whole boot. New scripts on b162: they work, but b162's `macSet` still sends its driver-mailbox 456, which the
DAL release doesn't clear, so UCLK stays at 456 or above (inferred: the higher floor wins). The scripts and the kext go
together.

**Not sent, as before (Linux sends them):** `SetHardMaxByFreq` UCLK = top at init (the PMFW's own maximum is the top
level: a no-op, unverified); `SetAlwaysWaitDmcubResp` (0x14 hung the PMFW with the GOP's DMCUB at b76, the kext refuses
it); FAMS. `GetDcModeMaxDpmFreq` is not read (the soft max is off on Linux).

**Unchanged:** `b15_boot.sh` (upstream's XT recipe, not run on the XTX machine) still calls `uclk.sh pin 456`; the new
`pin` ignores the number and pins at the top level. The `phxboot-uclk` file's content is no longer read.

## 7. Open points

1. **240 Hz without FAMS.** Linux's 96 MHz floor at 240 Hz goes with FAMS; on macOS the same floor (released by
   `idle_dpm.sh`) has no FAMS behind it. The log shows no underflow re-pin in 43 releases at 240 Hz, but UCLK rarely
   switched there before VRAM BOs: the load check in section 6 is what tells. If it underflows, the Linux-consistent
   answer without FAMS is to keep UCLK at the top level at 240 Hz (idle power) until FAMS exists on macOS (K11 or
   later, its own review).
2. **Idle power while pinned.** 1249 instead of 456 from the bring-up to the release, and for the whole boot where
   `idle_dpm.sh` doesn't release (no `phxboot-idledpm`: the release package's first-boot flag set, `phxboot-sdma`,
   `phxboot-cg`, `phxboot-uclk`; a pipe-1 boot; a baseline underflow). The release set should get `phxboot-idledpm`
   (+ `-dcf`), which the XTX machine has run since 2026-11-23: the owner's call.
3. **Mode switches while released** skip Linux's raise to 1249 around a 240 Hz switch (`dcn32_prepare_bandwidth`), as
   before U1; the replay engine's switches are inside the watchdog's blind window (a switch's blank). K11 moves the
   raise and lower into the kernel with DC's rule (B1 condition 15).
4. The `ReturnHardMinStatus` bits on macOS: on the GOP's state (no DPREFCLK hard minimum ever sent) the DPREFCLK bit
   may differ from Linux's (unverified; the traces show one read per hard minimum, not its value). A status that never
   comes is only logged, as in Linux.
5. `SetHardMaxByFreq` UCLK = top at init is not sent (a no-op if the PMFW's maximum is the top level, unverified).
6. Before U1 and unchanged: `idle_dpm.sh` sends the UCLK release before `SetFclkSwitchAllow 1`; Linux's optimize pass
   sends the FCLK message first (`dcn32_clk_mgr.c` v6.8 :633-641 before :710-720). Its own change and review.

## 8. hw-safety review

`hw-safety-reviewer`, 2026-11-26, on the diff and this note against Linux v6.8 and master (read-only, nothing run on
hardware). Verdict: **SAFE WITH CHANGES**, one blocking finding, folded in:

- **Blocking, fixed:** the status poll went on after a status read that wasn't answered OK (up to 200 reads, each with
  its own 200 busy retries); Linux stops there (`dcn32_clk_mgr_smu_msg.c` v6.8 :147, :252). `uclk.sh` now stops at the
  first failed read; `uclk_test.sh` `status_read_fails` and a mutation cover it.
- **Fixed:** `debug.phxpipe0_uclk` accepted 96-2500 MHz, which would replace the daemon's DAL hard minimum and could
  lower it; b167 takes only 0. The note's claim that the traced poll stopped "only on 0x24" (section 2.4), the missing
  watermark-order note (section 3), the deploy coupling (section 3) and a comment in `phx_debug.cpp` ("above" for
  "below") are corrected. The `uclk.sh` header says that the 96 MHz release at 240 Hz goes with FAMS on Linux.
- **Confirmed:** mailbox registers, message ids, argument encoding, table read, the top level as Linux's "UCLK min =
  max", the status bits and the PMFW version gate; the boot order (SMU block before display); no other sender of
  driver 0x1B / 0x1C in the tree; SMU 13.0.0 wires no hard-limit hook. Pinning at the top level is safer than 456 (no
  UCLK switch at all while pinned).
- **Not blocking, carried over, open:** the release to 96 MHz at 240 Hz departs from Linux, which holds 96 there only
